### Case Study – 2 (SLO-2): Applying ONOS in a Large-Scale SDN Deployment

---

### a) How ONOS Achieves Scalability and Fault Tolerance

To manage a nationwide infrastructure with thousands of switches and millions of flows without creating a single point of failure or performance bottlenecks, ONOS relies on a distributed, active-active clustered architecture:

* **Distributed State Management & Horizontal Scalability:**
* **Scale-Out Clustering:** Rather than relying on a single large server or passive standby backup, ONOS deploys an active-active cluster of server nodes. When network size increases, the ISP simply adds new ONOS instances to the cluster without reconfiguring the underlying network.
* **Distributed Data Stores (Atomix / Raft Consensus):** ONOS partitions and replicates its internal state (topology graph, flow tables, device registry) across nodes. It balances data handling by using:
* **Strong consistency (Raft consensus):** For mission-critical state where correctness is vital (device mastership assignments, intent states).
* **Eventual consistency (Anti-entropy protocols):** For rapidly fluctuating, lightweight state (link metrics, packet counters) to avoid distributed synchronization overhead.


* **Workload Partitioning:** Nationwide devices and switches are distributed across cluster members. Each node actively handles a subset of the data plane rather than one node processing every packet-in event.


* **Carrier-Grade Fault Tolerance and High Availability (HA):**
* **Mastership Election and Automatic Failover:**
* For every switch in the nationwide network, the ONOS cluster designates one node as the **Master** (handling flow rule updates and packet-in messages) and assigns multiple other nodes as **Standby Backups**.
* If the primary master node crashes, loses power, or suffers a link partition, the remaining cluster nodes detect the failure within milliseconds via heartbeats.
* A standby node is elected as the new master via Atomix consensus, taking over switch communication seamlessly with zero loss of forwarding state or control-plane disruption.


* **Zero Downtime for the Data Plane:**
* Switches maintain their active hardware flow tables during controller failovers.
* In-flight nationwide customer traffic continues to pass uninterrupted at wire speed while the control plane reassigns mastership roles.

### b) How ONOS Applications and APIs Help in Dynamic Network Control

ONOS separates network control into high-level declarative logic, modular network applications (NetApps), and vendor-agnostic device drivers:

* **Intent Framework (Declarative Policy-Based Routing):**
* **Abstracted High-Level Policies:** Instead of writing low-level flow rules (match tables, actions, timeouts) switch-by-switch across the country, operators and apps submit high-level **Intents** (e.g., `HostToHostIntent` or `PointToPointIntent`) specifying *what* network behavior is desired (e.g., minimum 10 Gbps bandwidth, max 15ms latency, backup path reserved).
* **Intent Compilation and Enforcement:** The ONOS Intent Framework dynamically compiles these high-level requests into concrete, multi-stage flow objectives (Filtering, Forwarding, and Next objectives) and pushes them to switches along the calculated path.
* **Self-Healing Automation:** The framework continuously monitors intent states. If a backbone fiber cut occurs between two cities, the Intent Framework automatically detects the topological change, recalculates an alternate optimal path, and installs updated flow rules in real time without human intervention.


* **Northbound APIs for Dynamic Network Automation:**
* **REST / RESTCONF & Intent APIs:** Expose programmatic endpoints that allow the ISP's Business Support Systems (BSS), Operations Support Systems (OSS), and cloud orchestrators to provision dynamic bandwidth, establish on-demand customer VPNs, or trigger maintenance rerouting on the fly.
* **Event Streaming & Telemetry:** Northbound event listeners notify external monitoring tools of network health changes (link up/down, packet surges) so automation scripts can execute immediate policy shifts.


* **Driver Subsystem and Southbound Providers (Multi-Vendor Control):**
* **Device Driver Modularity:** The ISP's nationwide backbone contains switches from multiple vendors (e.g., Cisco, Juniper, Edgecore, white-box switches). ONOS uses a pluggable **Driver Architecture** that acts as an abstraction bridge between the core and the physical hardware.
* **Multi-Protocol Translation:**
* For OpenFlow-enabled switches, the OpenFlow Provider encodes flow objectives into standard table entries.
* For programmable P4 pipeline switches, the P4Runtime driver maps objectives to custom match-action pipelines.
* For optical transport elements (ROADMs) or traditional routers, NETCONF/YANG or gNMI drivers translate intent directives into device configurations.


* This allows the ISP to enforce consistent, dynamic routing policies across its entire multi-vendor network through a single, unified control plane.
